# F04 identity-policy anchor decision required - 2026-10-04

This note follows the accepted decision that standalone `agent_nft.agent_nft.mint` is normative and registry-side minting must reject. It does not reopen that choice. Implementation is blocked because the accepted applied-policy parameterization gives each bootstrap reference a distinct policy ID, while registry spend cannot authenticate a datum-supplied policy ID.

## Reviewed global-anchor candidate: rejected as specified

The candidate one-time global anchor UTxO would hold one canonical identity policy ID and be enforced by registry reference inputs. The security review found this incompatible with the approved design: `agent_nft` takes `bootstrap_ref` as an applied parameter, and that reference is consumed per registration and included in the identity name. Different refs produce different applied policy IDs; one consumed seed supports only one mint under its applied policy. One global datum cannot authorize multiple registrations in that model.

The abstract dependency graph could be acyclic if anchor scripts are fixed first, registry pins their script/token IDs, registry hash then determines the shared identity-policy ID, and an authorized anchor transaction commits that ID. But that graph requires changing identity mint semantics to a shared policy ID.

## Owner must choose the identity-policy model

**A. Shared identity policy ID.** Remove per-identity `bootstrap_ref` from the applied policy parameters and put the seed reference in the mint redeemer. Keep the current name formula’s DID/owner/seed binding and require exactly one consumed seed for every identity mint. A single immutable global anchor can then commit one shared policy ID. Its one-time initializer needs an explicitly approved project-level authority set; founder plus a global 3-of-5 guardian quorum is one proposal, not an accepted authority decision. This revises the F04 policy interface, serialized policy IDs, migration, and tests.

**B. Per-identity policy IDs.** Retain `bootstrap_ref` as an applied policy parameter. Use one fixed shared anchor script and minting policy, independent of registry/NFT hashes. Each identity anchor is issued in a separate earlier transaction using `anchor_seed` in the shared policy redeemer (never as an applied parameter); this seed is distinct from the later-consumed `bootstrap_ref`. Derive its token name from a domain-separated formula including `anchor_seed` and the identity tuple, store the seed in immutable datum, and mint exactly +1 at the fixed unspendable anchor script. The anchor binds the resulting per-identity policy ID, exact DID, founding owner, bootstrap ref, identity asset name, and initial guardian set. The owner plus 3-of-5 signatures from that committed set authorize the ID; registration later requires all five guardian signatures under the accepted design. Registry and standalone mint each require exactly one matching anchor reference in that transaction, and registration consumes the original bootstrap ref. The same anchor UTxO can be used as a reference by both transactions and cannot be spent, mutated, or burned. A different anchor seed can create another quorum-authorized candidate for the same identity tuple; the owner must accept that while bootstrap single-spend limits final registration to one, or approve stateful uniqueness. The quorum authorizes the policy hash but cannot on-chain prove source/build identity, so the signers must independently verify reproducible source, parameters, and policy ID. Registry upgrades need a separate migration design. This option adds a prior transaction and a new anchor lifecycle/test surface.

Both choices preserve standalone minting and registry-side mint rejection. Both require exact policy provenance, anti-substitution checks, an acyclic parameter graph, and independent design review. A datum-supplied policy ID alone is not an anchor; the F05 authority singleton does not currently provide this function.

## Design-review test requirements

Cover the compiled dependency graph and exact applied hashes; missing/wrong/duplicate anchor references; wrong singleton token or datum; alternate policy; wrong policy ID/name/DID/owner/bootstrap binding; absent/insufficient/duplicate/non-guardian authorizations; replay or attempted replacement; exact token quantity and unique inline registry output; and paired success of standalone mint plus `RegisterAgent`. Under A, also prove repeated identities use distinct consumed seed refs under the same policy ID. Under B, prove anchor authorization precedes registration, anchor_seed is distinct from bootstrap_ref, the same seed-bound token cannot be reissued, a valid anchor reference may be reused across the paired transactions, and the agreed multiple-anchor/uniqueness rule is enforced. Aiken helper tests alone do not establish paired Plutus V3 transaction behavior.

No tests were run for either candidate. The Aiken 122/122 baseline applies only to current source; paired evaluator, ledger, and live evidence are absent. Readiness remains NOT READY and gated actions stay disabled.


## Refined per-identity anchor conditions from independent review

The shared anchor policy must keep one fixed applied policy ID: put each `anchor_seed` in its mint redeemer, not applied parameters. Derive the anchor asset name with a domain-separated formula that includes `anchor_seed` and the committed identity tuple; include the seed in the immutable datum and have the registry derive and check the same name. Require the exact seed input and exactly +1 of that token. Keep `anchor_seed` separate from `bootstrap_ref`; anchor issuance is a prior transaction and must not consume the bootstrap that registration later consumes.

Bind each immutable anchor datum to `anchor_seed`, policy ID, DID, founding owner, bootstrap ref, identity name, and initial guardian set. Both standalone mint and registry require exactly one matching reference input within that transaction; this is not a global one-anchor-per-identity guarantee. Anchor issuance requires owner plus 3-of-5 signatures from the committed guardian set. RegisterAgent separately requires owner/controller and five transaction-bound signatures, one from each anchored guardian. The anchor output is locked at the fixed unspendable script and cannot be spent, mutated, or burned. A consumed seed-bound token cannot be reissued; a different seed can produce a second authorized pre-registration anchor for the same identity tuple unless stateful uniqueness is added.

Distinct anchor seeds do not prevent multiple quorum-authorized anchors for the same identity tuple. Owner must accept multiple pre-registration authorization candidates while bootstrap consumption allows at most one final registration, or authorize a stateful uniqueness mechanism. On-chain checks cannot prove the selected policy ID came from the intended source build; authorizers must independently verify the reproducible source/build/parameters/policy ID and preserve provenance. The immutable anchor also requires a separate registry-upgrade/migration design. This candidate is suitable for owner review only with these choices explicit; it is not implementation-ready.
