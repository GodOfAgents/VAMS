# F04 Option B anchor contract — design only

Status: frozen design candidate for independent review. No implementation, compiled-execution, ledger-admission, live-network or compatibility acceptance is granted. Owner selection permits multiple quorum-authorized candidate anchors with different anchor seeds. Registration is single-use per committed bootstrap; global DID uniqueness is not established.

Standalone `agent_nft` is the sole target V2 identity mint/burn policy. Every mint-purpose branch of the NEW V2 registry R must reject, including its V2 mint and burn actions. Existing V1 validators/policies retain their original meaning; this design neither changes nor qualifies V1 legacy burn behavior, whose earlier evidence remains historical. The new V2 registry authenticates a policy ID through the independent anchor token and fixed address, replacing the existing policy-ID-equals-own-script-hash coupling only after implementation review. F05 singleton, committee, reserve value and genesis flags confer no F04 authority.

## Acyclic script dependency graph

1. Compile fixed shared anchor lock S0, with no parameters and rejection on every spend/other purpose.
2. Compile fixed shared anchor mint policy P0, parameterized only by S0; its shared applied policy ID stays constant across identities. Every burn or unsupported purpose rejects.
3. Compile shared V2 registry R with S0 and P0 as fixed trusted applied parameters; no identity/bootstrap/NFT hash parameter.
4. Apply standalone identity policy N with ordered parameters bootstrap_ref, R, S0, P0. Each bootstrap therefore retains its own identity policy ID.
5. Off-chain construct anchor datum containing the already computed R/N identifiers. P0 checks these supplied commitments structurally and requires founder/quorum authorization. P0 does not compile against R/N; the datum cannot create a hash cycle.

Every hash is the exact ledger Plutus V3 applied-script hash/policy ID (28 bytes), never a SHA-256 source hash or blueprint's unapplied hash. This design assigns role names, not invented final hash bytes. Final bytes, parameter encodings and V3 language hash prefixes must be frozen by later reproducible-build evidence.

## Genesis ordering and bootstrap cycle elimination

Create a registry PreGenesisV2 seed UTxO first. Its own output reference is bootstrap_ref. The pre-genesis datum contains no own reference, NFT policy ID/name, anchor token name, or other future-dependent hashes: committing them in its creating transaction would create a transaction-ID cycle. After this genuine UTxO exists, compute N and issue an anchor in a separate earlier transaction. Issuance consumes distinct anchor_seed and references, but never consumes, bootstrap_ref. Then one atomic transaction executes standalone MintIdentity and registry RegisterAgent, consuming the exact bootstrap_ref as the unique registry pre-genesis input.

The seed output address is exactly R with no stake credential; inline PreGenesisV2 fields, field order and constraints are frozen in CONSUMER-CONTRACT.json. Its value is ADA only and exactly the committed initial stake. A synthetic seed-shaped output alone conveys no authority: the paired registration verifies founder/controller/all-five guardian signatures and the valid earlier anchor.

## Frozen anchor datum and name

ANCHOR-CONTRACT.json is normative for ordered datum fields, constructors, widths, raw token-name serializer, bounds and independently serialized synthetic vector. AnchorDatumV2 is a distinct Data constructor 0 with exactly the 17 listed fields. OutputReference is Data constructor 0 containing [32-byte transaction ID, unsigned-32 output index]. Guardians are a Data list of five raw 28-byte key hashes in strict ascending byte order. Datum integers are Data integers with explicit range checks; no missing fields/defaults/coercion/extra constructors.

The existing identity name remains Blake2b-256 of ASCII VAMS/agent/v1 plus NUL, u16 DID byte length, exact DID bytes, founder VKH, bootstrap transaction ID and u32 output index. Anchor name uses a separate VAMS/agent-anchor/v2 plus NUL domain, includes both references and every committed identity/genesis field, and is exactly 32 bytes. It does not hash its own derived anchor name. No Unicode normalization or ASCII-hex reinterpretation is allowed.

## Anchor issuance public boundary

P0's one supported redeemer is IssueAnchor, Data constructor 0 containing [anchor_seed OutputReference]. No applied seed parameter exists. Require exactly one consumed input with that reference, and anchor_seed != bootstrap_ref. Equality would require the same UTxO to be consumed and referenced; that case is helper/invalid-context evidence only and earns no compiled-negative or ledger-admission credit. Require exactly one reference input with bootstrap_ref, an actual PreGenesisV2 output at datum R, and equality of DID, founder/controller/operator, guardians, metadata and stake against the proposed anchor. Reference presence must be genuine ledger-resolved evidence for ledger-admission credit.

Require founder plus at least three distinct keys from the exact five committed guardians in the ledger-validated body signer set. Guardians are pairwise distinct and disjoint from founder/controller/operator. Registration separately requires founder, initial controller and all five guardians; issuance quorum does not replace genesis proof of possession. These signatures commit the transaction body including datum, script/policy ID and output. Signatures for another body, seed, policy, tuple or guardian set cannot substitute. Pure duplicate-list tests do not represent valid ledger signer sets.

Require tx.mint to contain exactly one non-ADA entry: P0/derived-anchor-name +1. Require exactly one output carrying that asset, quantity exactly 1, at exact S0/no-stake address, inline AnchorDatumV2, no reference script, ADA equal anchor_lovelace and no other assets. Every datum field and name is verified. The lock S0 cannot spend; P0 cannot burn. Consequently the anchor cannot be moved, modified, retired, burned or reissued using its consumed seed.

The same anchor reference output is available to the standalone policy and registry spend in one registration transaction; they independently inspect the same ledger reference set. An anchor may remain referenced throughout that identity's later allowed transitions. No anchor read decrements supply or consumes it.

## Paired registration and mutable-state projection

Each public entrypoint requires exactly one matching anchor reference in its bounded transaction. A match includes exact S0 address, P0 token/name/quantity/value, inline datum, all checked bounds, and full tuple equality for genesis (including N, R, DID, founder, bootstrap, identity name, initial controller/operator/guardians/metadata/stake and zero genesis epochs). N checks datum.identity_policy_id equals its own mint-purpose policy ID; R checks the same exact approved ID against the mint and unique state output. Wrong/datum-supplied unanchored policy IDs reject. Both require one consumed exact PreGenesisV2 bootstrap input and one exact V2 continuing state output, +1 of the same identity name, no extra minted identity or extra matching state input/output, complete transaction value conservation and valid funding witnesses.

The NEW V2 R's mint-purpose path is unconditional rejection; no V1 legacy burn behavior change is claimed. Standalone policy success alone earns no paired acceptance; registration must execute R.RegisterAgent over that same transaction and body. Non-RegisterAgent/wrong-purpose/wrong-redeemer contexts reject.

After registration, anchor genesis fields remain immutable historical commitments. Recovery compares the stable DID, founder, bootstrap, N/name/R identity projection to the anchor, validates the anchor itself fully, and checks current controller/guardian/epochs through the prior V2 state and accepted recovery transitions. It must not force current controller/guardians/operator/metadata/stake back to genesis values. The accepted 3-of-5 recovery, 48h/7d/14d delays, destination proof of possession, freeze, monotonic nonces/epochs, exact value/identity preservation and no administrator takeover remain unchanged. Standalone terminal burn binds the exact authorized deregistration request and current-controller payout; immutable initial owner never substitutes for current authority.

## Candidate multiplicity and guarantees

Different consumed anchor seeds may issue multiple founder-plus-quorum-approved anchors for one bootstrap, including differing authorized policy/initial candidate commitments consistent with the seed constraints. Only one candidate anchor may match in a registration transaction; supplying two matching references rejects. This is transaction-local ambiguity prevention, not global anchor uniqueness.

Within the reviewed and pinned VAMS R/N route, every successful registration under an authorized candidate must consume the same genuine bootstrap_ref. Cardano ledger single-spend permits at most one of those competing registrations to be admitted, regardless of differing anchor seeds or policy IDs. This guarantee applies only to that reviewed route: P0 quorum authorization cannot establish bootstrap consumption or registration semantics for arbitrary alternative code. Two evaluator simulations can both return True on conflicting inputs; that alone does not prove ledger single-spend. Later ledger-admission conflict evidence is mandatory. Distinct bootstrap references may register the same raw DID and founder; no cross-bootstrap uniqueness, personhood, custody independence or canonical-DID selection is claimed.

Quorum compromise or mistaken approval can authorize an alternative compiled policy. The anchor authenticates their policy-ID choice, not that code's provenance. Authorizers must independently verify intended source, dependency/compiler pins, immutable script bytes, parameter encoding/order and applied IDs; compare independently reproduced N/R/S0/P0 builds and the exact signed body. Their signatures do not prove compiler/source identity on-chain. The reviewed/pinned VAMS route enforces its on-chain identity guards and ledger single-spend; arbitrary quorum-approved alternative code receives no such behavior guarantee. No proof of source audit or real-world guardian independence is manufactured.
