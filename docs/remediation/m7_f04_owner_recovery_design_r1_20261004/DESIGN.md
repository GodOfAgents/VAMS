Before F04 implementation, make the standalone policy the sole identity mint/burn authority and make the registry-side mint purpose reject. The standalone mint branch itself must require exactly one consumed input at its parameterized registry validator hash, consume the designated bootstrap reference exactly once, require `tx.mint` to contain exactly one +1 identity token, and require exactly one registry-script output with inline datum matching the identity tuple and carrying that token. This makes a mint-only transaction fail even when no registry validator would run. The payout must equal all non-identity value in the registry input; transaction fees must be funded by other inputs. All native assets from that input go to that one payout, with no split, redirection, or retained state value. Both scripts reject extra matching registry inputs, ambiguous payout outputs, wrong beneficiary, partial burn, or unrelated datum/redeemer. These requirements are a design target; test their actual Plutus V3 redeemer/context semantics before implementation acceptance.

## 2. Identity model and continuity

Introduce a future `AgentDatumV2`; do not decode `AgentDatumV1` as V2 or silently migrate existing UTxOs. The new datum carries:

- immutable `did`, `identity_policy_id`, `identity_asset_name`, `bootstrap_ref`, and `founding_owner_vkh`;
- mutable `controller_vkh` (the current root owner/control key) and operator;
- five distinct guardian verification-key hashes, fixed threshold 3-of-5, and an unsigned-64-bit `guardian_epoch`;
- monotonic unsigned-64-bit `state_nonce` and `control_epoch`;
- `frozen` and optional `pending_control_change` state;
- existing economic and reputation fields, retained unchanged by recovery transitions.

At genesis, derive the identity asset name in the standalone mint policy as `blake2b_256(ASCII("VAMS/agent/v1") || NUL || u16_be(length(did_utf8)) || did_utf8 || founding_owner_vkh[28] || bootstrap_tx_id[32] || u32_be(bootstrap_output_index))`. `did_utf8` is the exact valid UTF-8 byte sequence stored in the datum, with no Unicode normalization; require valid UTF-8 DID bytes of length 32 through 256 inclusive, preserving the current `valid_did` acceptance range, exact field widths, and an output index fitting unsigned 32-bit. This is the domain and serialization already used by the current pure helper, but its public mint handler is fail-closed. The policy is parameterized with the generic registry validator hash and bootstrap reference; the registry validator is not parameterized by the identity policy ID, avoiding a circular script-hash dependency. The registry registration spend validates the same transaction’s `tx.mint` entry, the consumed bootstrap input, and exactly one matching output containing the newly minted token and unique registry datum; a newly minted token is not treated as an input in that transaction. The token remains quantity one under the same policy and asset name for the full identity lifetime. Recovery changes only `controller_vkh`, epochs/nonces, and pending/freeze fields. It never changes DID, founding owner, bootstrap reference, policy/token identity, stake, reputation, metadata, authorized slashers, or value. A distinct V2 datum and identity derivation require review against canonical source before implementation.

Prove genesis controller and guardian key possession with transaction signatures: require the immutable founding-owner VKH, the initial controller VKH, and all five guardians in the ledger-validated `extra_signatories` set for the registration transaction (if founder and controller are the same key, one valid signature satisfies both roles), whose signed body includes the identity mint, exact bootstrap input, and registry output/datum containing the canonical guardian set and genesis epoch. For controller rotation/recovery, require the destination controller VKH in the scheduling transaction signer set; the signed body includes the exact committed request ID and destination. For guardian rotation, require all five proposed guardian VKHs in the scheduling transaction signer set; the signed body commits to the request ID and canonical ordered guardian set. These are Cardano transaction-body proof-of-possession checks, not user-supplied booleans or detached signatures. Guardian VKHs must be pairwise distinct and permanently disjoint from the founding-owner VKH, current controller VKH, and current operator VKH. The controller and operator may equal one another or the founding owner, but neither may equal a guardian. Every new controller/operator destination and every proposed guardian set must preserve these constraints atomically; a proposed guardian set must also be internally pairwise distinct. Count authorization by the intersection of the five canonical guardian VKHs and the ledger-provided transaction signer set; ledger-valid contexts represent signers uniquely. Duplicate-list tests belong in pure helper/property tests, not claims about valid ledger contexts. On-chain checks establish distinct keys and valid signatures, not independent real-world custody; the registration procedure must document five separately controlled guardians. No global or protocol administrator key is a recovery authority.

## 3. Recovery authority and transitions

The authorization listed for each action is checked when the pending action is scheduled. After the authorized request is committed in the unique identity datum, any submitter may execute only that exact action after its delay and before expiry; the executor cannot change its destination, identity, epochs, or payout. Guardian cancellation remains available under the quorum below.

| Action | Authorization | Delay | Effect / limits |
|---|---|---:|---|
| Routine controller rotation | Current controller + 2 distinct current guardians + new-controller proof of possession | 48 hours | Schedule immediately; execute only after delay. |
| Lost/compromised controller recovery | 3 of 5 distinct current guardians + new-controller proof of possession; old controller not required | 7 days | Freeze ordinary state changes at schedule time; then rotate controller. No current-controller veto. |
| Emergency freeze | 3 of 5 distinct current guardians | Immediate | Freeze ordinary metadata/operator/economic/deregister transitions, clear any pending request, and increment state nonce. Cannot move value, change controller, change guardians, or burn. A separately authorized slash transition remains available if and when its independent activation gate passes. |
| Unfreeze | 3 of 5 distinct current guardians | 48 hours | Clear freeze only after delay; no other datum/value changes. |
| Guardian-set rotation | 3 of 5 current guardians + proof of possession from each of 5 proposed distinct guardians | 14 days | Replace guardian set atomically; keep threshold 3-of-5; increment guardian epoch. |
| Cancel pending action | 3 of 5 distinct current guardians | Immediate | Clear exactly the pending request and increment only state nonce. Controller/guardian epochs do not change unless the corresponding authority actually changes. Current controller alone cannot cancel recovery. |
| Expire pending request | Permissionless after its expiry bound | Immediate after expiry | Clear pending request without authority transfer. Preserve any freeze that predated scheduling. |
| Voluntary deregistration | Current controller + 3 of 5 guardians | 48 hours | Schedule a terminal request; after delay, burn the exact NFT and pay all non-identity assets to the fixed current-controller key address. No administrator burn or recovery bypass. |

A guardian quorum can freeze an identity or recover its controller; that is the explicitly selected recovery authority. No single administrator or guardian can take over, freeze, unfreeze, rotate a controller, rotate guardians, or burn the identity. Compromise of 3 current guardians defeats this threshold; this is a residual quorum risk, not something a hidden administrator key may bypass.

A scheduled recovery freezes immediately so a compromised old controller cannot race the timelock by changing operator, metadata, stake, or deregistering. Recovery and guardian-set rotation remain available while frozen. Slash/action authority (including any `RegistryAuthorityV1`) cannot authorize recovery, and recovery cannot create slash authority or enable Slash activation.

## 3a. Pending-action state machine

`pending_control_change` is a tagged union with exactly one of `ControllerRoutine`, `ControllerRecovery`, `GuardianRotation`, `Unfreeze`, or `Deregister`; at most one pending action may exist. Each variant stores its destination commitment, request ID, base nonce, both authority epochs, execute/expiry bounds, and action-specific authorization evidence/commitment. If current state nonce is N before scheduling, the request stores `base_nonce = N` and scheduling writes state nonce N+1. Execute, cancel, or expiry verifies the exact pending request committed at scheduling, its stored base nonce, and unchanged bound control/guardian epochs. The current state nonce must be at least base_nonce+1. Only an independently authorized slash may advance state nonce while preserving the pending request; after such a slash, completion or cleanup increments the current nonce by exactly one. A terminal deregistration consumes the current pending state and creates no continuation. No new pending request can replace another. While any request is pending, ordinary update/operator/stake/value/deregister transitions are blocked. An independently authorized slash transition may consume the state UTxO only if it preserves every pending-request byte and all controller/guardian fields, changes only slash-authorized state plus the monotonic state nonce, and satisfies the existing slash authority and activation gates. This transition does not invalidate or rewrite the scheduled request; its request ID remains bound to the stored base nonce and epochs. The pending action's execution, guardian-quorum cancellation, a quorum emergency freeze (which clears pending), or permissionless expiry cleanup may also consume the state UTxO.

Emergency freeze is allowed with or without a pending request. It sets `frozen = True`, clears any pending action, and increments `state_nonce`; it does not change `control_epoch` or `guardian_epoch`. A fresh recovery/guardian-rotation/unfreeze request may then be scheduled under the frozen-state rules. A pre-existing freeze is never cleared by cancel or expiry. Recovery execution leaves the identity frozen; unfreeze is a separate request. While frozen, only controller recovery, guardian rotation, cancellation/expiry cleanup, a scheduled unfreeze, and an independently authorized slash transition may proceed. Slash remains subject to its separate activation criteria and cannot change or clear the recovery request, controller, guardian set, or their epochs. Deregistration cannot be scheduled or executed while frozen. A guardian quorum may cancel any pending action, including deregistration or unfreeze; controller-only cancellation is never valid.

Every transition that consumes and recreates the identity state increments unsigned-64-bit `state_nonce` exactly once, including ordinary metadata/operator/stake/slash transitions, pending request scheduling, execution, cancellation, expiry, freeze, and unfreeze. A terminal deregistration checks the stored pending request and has no continuation. If input nonce is N, an ordinary transition outputs N+1. A pending request scheduled from input nonce N stores base N and outputs nonce N+1. It normally completes/clears from N+1 to N+2; if one or more independently authorized slash transitions occurred while pending, it completes/clears from the then-current nonce N+k to N+k+1. Only those slash transitions may advance the state nonce without clearing pending. `control_epoch` increments only when `controller_vkh` actually changes. `guardian_epoch` increments only when the guardian set actually changes. Scheduling, freezing, cancellation, cleanup, and unfreeze do not increment either authority epoch. Request approval binds the stored base nonce and both current epochs; slash preserves the committed request exactly and does not change epochs. Clearing/completing a request increments the current nonce, so stale requests cannot be replayed. Cancellation/expiry changes no authority. Emergency freeze cancels an unfreeze request, preventing it from later clearing the freeze.

## 4. Timelock, replay, and transaction binding

The request transition writes one pending request into the unique identity UTxO. It contains action kind, destination controller or guardian set hash, request ID, base state nonce, control epoch, guardian epoch, `execute_after`, `expires_at`. A request is authorized against the current datum and current UTxO only.

Use POSIX milliseconds and exact delays: 48 hours = 172,800,000 ms; 7 days = 604,800,000 ms; 14 days = 1,209,600,000 ms; 30 days = 2,592,000,000 ms; maximum transaction interval width = 300,000 ms. At scheduling, accept only a finite, closed/inclusive lower and upper bound, with `0 <= lower <= upper`, width <= 300,000 ms, and checked additions for `execute_after = upper + delay` and `expires_at = execute_after + 2,592,000,000`. Anchoring the delay to the latest possible schedule inclusion time `upper` guarantees the full stated delay even if the schedule transaction lands at the end of its validity interval. Plutus V3 bound constructors must be finite and inclusive; reject open bounds, exclusive bounds, reversed bounds, and unbounded ranges. Using the latest included scheduling time is conservative for a minimum timelock: real schedule inclusion cannot be later than `upper`. At execution, require both finite inclusive bounds, `lower >= execute_after`, `upper <= expires_at`, `lower <= upper`, and interval width <= 300,000 ms. Thus execution exactly at either inclusive boundary is permitted; one time unit before readiness or after expiry fails. Permissionless cleanup is permitted only when the finite inclusive lower bound is strictly greater than `expires_at`; it clears pending without transfer and preserves the current `frozen` bit. No action can automatically unfreeze. Terminal deregistration cannot be scheduled while frozen, and while any pending action exists no second pending action can be scheduled. These interval constructor and comparator rules are required to be verified against the actual Plutus V3/Aiken ledger API before implementation.

`request_id` is the 32-byte `blake2b_256` digest of this exact byte sequence: ASCII `VAMS/agent-control/request/v1` followed by one NUL byte; 28-byte identity policy ID; 32-byte identity asset name; 32-byte bootstrap transaction ID; bootstrap output index as unsigned 32-bit big-endian; one-byte action tag (`0x01` routine controller rotation, `0x02` controller recovery, `0x03` guardian rotation, `0x04` unfreeze, `0x05` deregistration); 28-byte current controller VKH; 32-byte destination commitment; stored base state nonce, control epoch, guardian epoch, execute-after, and expiry as unsigned 64-bit big-endian integers. The controller destination commitment is `blake2b_256(ASCII("VAMS/agent-control/destination-controller/v1") || NUL || destination_controller_vkh)`. Guardian rotation commits to five 28-byte VKHs sorted in ascending bytewise order using `blake2b_256(ASCII("VAMS/agent-control/destination-guardians/v1") || NUL || guardian_1 || ... || guardian_5)`; the datum stores that same canonical order. Freeze is immediate and has no pending request ID. Every field width and byte order is fixed; reject out-of-range values before serialization. The request includes the exact current identity token and is executed by consuming the unique current state UTxO. Request ID recomputation uses stored scheduling fields, not the later global state nonce, so an independently authorized slash can advance the nonce without changing the committed request. `state_nonce`, `control_epoch`, and `guardian_epoch` are unsigned 64-bit values. Every required increment is checked before the transition; reject rather than wrap if a value is already `2^64-1`. Controller/guardian epoch increments fail closed at that bound. A pending request may be scheduled only when the base nonce is at most `2^64-3`, reserving the schedule increment and at least one completion increment. A separately authorized slash while pending is accepted only when it leaves room for one pending completion increment. `state_nonce` increments once for every successful state transition. `control_epoch` changes only on completed controller rotation/recovery; `guardian_epoch` changes only on completed guardian rotation. The stored base nonce and both epochs are bound into the request ID; current control/guardian epochs must still match at completion. Enforce exactly one matching identity NFT in the single continuing registry output and preserve its full value for nonterminal recovery transitions.

## 5. Dependent identity continuity

The DID and identity NFT remain stable across controller recovery, but each authorization consumer must resolve the current `{identity_policy_id, identity_asset_name, controller_vkh, control_epoch}` from an authoritative registry view and compare every proof/credential to that tuple. If the registry view is unavailable or stale, owner-authorized actions fail closed. A TEE attestation must bind the root controller and control epoch; an epoch change invalidates existing attestations and requires a fresh attestation under the new root. A session-key grant must carry the control epoch; `sequence_wallet`/session verification rejects any grant from an older epoch immediately, while preserving the <=24-hour maximum and contract whitelist. OMS/agent credentials must bind controller and epoch; `OMSIdentityVerifier` rejects stale epoch or unavailable registry/identity evidence, preserving INV-5 fail-closed behavior. Authorization caches are keyed by identity NFT and epoch; on epoch mismatch they evict old entries and deny until fresh evidence is verified. Recovery does not revoke or renew credentials by itself; consumers enforce epoch checks. Targeted tests must prove the old TEE, session, OMS credential and cache entry all fail immediately after recovery, new-epoch evidence passes, offline/stale registry resolution fails closed, and session expiry/whitelist invariants remain intact. Until those consumer checks and tests are designed and independently reviewed, F04 implementation remains blocked.

## 6. Compromise and liveness handling

- Lost controller key: 3-of-5 guardians schedule recovery; the old key is unnecessary. Immediate freeze prevents old-key actions while the seven-day observer window runs.
- Suspected controller compromise: 3-of-5 guardians freeze immediately, then schedule the same recovery. The owner cannot veto or unfreeze alone.
- One or two guardian keys compromised: neither recovery nor guardian replacement is possible from those keys alone. Keep the identity frozen if the remaining custodians consider quorum compromise plausible.
- Three guardian keys compromised: attackers can freeze, cancel, rotate the controller after delay, and replace guardians after delay. No admin emergency override exists. Treat recovery as failed closed; any constitutional/key-reconstitution route is a separate governance design and gate.
- Malicious new controller: delay, immediate freeze, notice window, quorum cancellation, and the new key's proof-of-possession constrain risk; they do not prove the new controller's real-world identity.
- Compromised administrator: no administrator is included in this state machine, so administrator compromise provides no owner-recovery capability.
- Pending request expiry: anyone may clear it only after strict expiry; this cannot transfer control or alter the current frozen bit.
- Recovery on suspended/slashed state: recovery may rotate control but cannot unsuspend, restore stake, reverse slashing, or activate slash powers.

Implement only in a later bounded slice after the exact design and matrix hashes are independently reviewed; make standalone mint/burn the only normative NFT route and disable registry mint; verify target Plutus V3/Aiken time, datum, redeemer and cross-validator context semantics; resolve V1/V2 genesis or migration compatibility; add dependent-identity credential epoch tests; then obtain independent implementation review.
