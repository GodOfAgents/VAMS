## Current-source characterization (inspection only; not test credit)

The hash-bound current source facts in DESIGN.md are: `agent_nft` has `derive_identity_name`, but its public mint handler returns `False` for all redeemers and fallback fails; the current `agent_registry` mint purpose handles `MintIdentity` and `BurnIdentity`. This mismatch is the reason for the owner’s normative choice. These are source-inspection facts, not executed tests or accepted identity-policy evidence. The future acceptance cases below require standalone mint acceptance and registry-side mint rejection after implementation.

## Genesis and standalone identity NFT

1. Accept exactly one standalone-minted identity NFT only when the designated bootstrap reference is consumed as an input, the registration spend validates the same transaction’s `tx.mint` entry, and exactly one matching registry output/datum carries the token; DID/founding-owner/bootstrap-derived asset name matches the approved formula. Do not require the newly minted token itself as an input.
2. Reject absent or reference-only bootstrap input, wrong reference, wrong policy/name, quantity other than +1, multiple token names, duplicate registry identity state, missing founding-owner or initial-controller signature (unless the keys are the same), repeated/ambiguous field encoding, and missing/invalid signer proof from any of five guardians. Assert the 32–256-byte valid-UTF-8 DID boundary and reject malformed UTF-8 and out-of-range lengths.
3. Accept only five pairwise-distinct guardian VKHs at fixed 3-of-5 threshold, disjoint from founding owner/controller/operator. Reject duplicate keys, fewer/more keys, any guardian overlap with founding owner/controller/operator, missing guardian PoP, and PoP bound to another DID/policy/token/bootstrap/epoch. Controller and operator may equal one another or founding owner but never a guardian. Include positive fixtures for (a) controller=operator, (b) controller=founding owner with distinct operator, and (c) operator=founding owner with distinct controller; all five guardians remain distinct and disjoint. Count the intersection with the ledger signer set. Exercise duplicate list entries only in pure helper/property tests; reject invalid signer sets at the context-construction layer.
4. Reject any registry-side mint. Prove standalone mint remains the only normative identity creation path.
5. Burn only the exact identity NFT as part of the authorized terminal registry transition. Match exactly one registry input datum and its `DeregisterAgent` redeemer, pending request ID, controller, epochs, and interval. The registry validator enforces no continuation and exactly one controller-key payout of all input value except the NFT, with transaction fees funded separately. Reject arbitrary quantity -1 burn, ambiguous/extra matching registry inputs, wrong identity/asset/policy, partial burn, wrong/split payout, or unrelated redeemer.

## Controller rotation and lost-key recovery

6. Routine rotation succeeds only with current-controller signature, two distinct current guardian signatures, and destination-controller PoP. Reject controller alone, one guardian, duplicate guardian counted twice, non-guardian, stale guardian, destination equal to any guardian, and absent/invalid destination PoP. Preserve allowed controller/operator or controller/founding-owner equality when neither is a guardian.
7. Recovery succeeds with three distinct current guardian signatures and destination-controller PoP when old controller signature is absent. Reject two-of-five, single administrator, one/two guardian(s), duplicate key counted twice, non-guardian signer, destination controller equal to any guardian, old guardian set after epoch rotation, and identity/request substitution.
8. Verify immediate freeze on recovery scheduling; old controller cannot update, rotate operator, change value, deregister, or veto/cancel recovery while pending. Verify guardian quorum can cancel; controller alone cannot. Reject recovery destination equal to any guardian and assert guardian/key disjointness after every successful controller transition.
9. Recovery while suspended/slashed changes only control fields and does not unsuspend, restore stake/reputation, rewrite slashing evidence, or grant slash authority.

## Freeze, unfreeze, guardian rotation, and exit

10. Emergency freeze accepts 3-of-5 and applies immediately; reject one or two guardians, controller alone, global admin alone, and any output/value/controller/guardian-set mutation in the freeze transition.
11. While frozen reject ordinary update, operator rotation, stake/value transition, deregistration, Deposit, and ExecuteIntent. Accept a valid independently authorized slash only when its activation gate is separately open; assert it preserves pending request bytes, controller, guardian set, epochs, and request ID while advancing state_nonce exactly once. Reject unauthorized slash and any slash mutation of control/recovery fields. Keep deployment/Slash/Deposit/ExecuteIntent activation gates closed until their separate criteria pass.
12. Unfreeze requires 3-of-5 and exactly 48 hours. With no intervening slash, schedule from N to N+1 and execute/cancel/expire from N+1 to N+2. If an independently authorized slash occurs while pending, assert the request remains byte-identical and completion advances the then-current nonce by one. Reject one millisecond early, controller-only/admin-only unfreeze, changed value/identity, stale guardian epoch, and stale request replay.
13. Operator rotation outside a pending/frozen state rejects any destination equal to a guardian; verify after every accepted operator change that no guardian/controller/operator/founding-owner separation rule is violated. Guardian rotation requires 3-of-5 old distinct guardians and PoP by every proposed new guardian; delay is 14 days and threshold stays 3-of-5. Assert after every guardian/controller/operator mutation that guardians are pairwise distinct and disjoint from founding owner, controller, and operator; controller/operator may coincide with each other or founding owner only when not a guardian. Reject duplicate proposed keys, any proposed guardian equal to founding owner/current or destination controller/operator, missing/invalid PoP, early execution, stale epoch, old-set replay, unapproved threshold change, and mixed controller/guardian mutation.
14. Voluntary deregistration requires current controller + 3-of-5 guardians and 48-hour delay. A single tagged pending request blocks all ordinary transitions; guardians may cancel it, and anyone may expire it only after the specified strict expiry boundary, with no burn or payout. After delay, payout goes only to current controller, equals all non-identity value from the state input, and transaction fees come from other inputs; the exact identity token burns and no continuing identity output remains. Reject owner-only or administrator burn/payout, early payout, partial burn, split/alternate beneficiary, unrelated redeemer, extra matching registry input, and recovery bypass.

## Time, replay, UTxO concurrency, and exact continuity

15. For each delay, accept a finite closed/inclusive execution interval beginning exactly at `execute_after`; reject one POSIX millisecond before, and accept an interval ending exactly at inclusive `expires_at` while rejecting one millisecond after. Pending cleanup requires a finite inclusive lower bound strictly greater than expiry. At scheduling, require finite closed/inclusive lower and upper bounds, nonnegative ordered bounds, and width <=300,000 ms. Anchor `execute_after` to schedule `upper + delay`; simulate schedule inclusion at `upper` and reject execution at `upper + delay - 1 ms`, accepting only at/after `upper + delay`. Reject open/exclusive/reversed/missing ranges, width >300,000 ms, and checked-add overflow.
16. Reject request-ID mutation, action/destination/context substitution, stale base nonce/control epoch/guardian epoch, approval replay after cancellation/expiry, approval replay after another transition, and two competing spends from the same identity UTxO. An arbitrary executor may submit the exact committed action after delay, but cannot change destination/payout/identity or epochs. Accept exactly one ledger-valid spend and continuation.
17. Emergency freeze increments the current state nonce exactly once whether or not pending state exists, clears pending, and invalidates that request; if an independent slash advanced nonce while pending, freeze advances from that current value. A pending action is a tagged union and at most one may exist. Reject scheduling a second request; allow 3-of-5 guardian cancellation of any pending kind; controller-only cancellation fails. Permissionless cleanup requires finite inclusive lower bound strictly greater than expiry, clears pending without burn/payout/transfer, and preserves the current frozen bit.
18. Every nonterminal transition advances the current state nonce exactly once. A scheduled request stores base_nonce N and outputs N+1; execute/cancel/expiry requires current nonce >=N+1, exact stored pending fields/request ID, and unchanged control/guardian epochs, then outputs current nonce+1 (terminal deregistration has no continuation). A separately authorized slash while pending preserves the request bytes and advances the nonce once; later request completion advances from that newer nonce. Stale, replayed, or skipped nonce fails. Every recovery/control-only nonterminal transition has exactly one same-script continuing identity output with exactly one same-policy/token NFT and exact value equality. An independently authorized slash follows its separately accepted F05 value-routing rules while preserving the pending control request; other action classes follow their own accepted value rules. DID, founding owner, bootstrap, policy/token, stake, reputation, metadata, slashers, and unrelated fields remain byte-for-byte/semantically unchanged except fields expressly changed by the separate authorized slash. Only authorized controller/guardian/operator/pending/freeze/nonce/epoch and slash fields may change; every post-transition key set must preserve guardian disjointness.
19. For recovery/control-only transitions, wrong or missing identity token in continuation, multiple candidate continuations, extra identity token, value loss/gain, duplicate datum, altered immutable field, or silent datum-version migration fails. Slash value movement follows separately accepted F05 routing rules. Terminal deregistration has no continuation and routes every native asset from the state input to one exact current-controller payout; registry-input value cannot fund fees, which must come from other inputs.

## Dependent credentials and test layers

20. Consumer-level epoch invalidation: TEE verifier rejects old root/epoch attestation and accepts fresh one; session-key verification rejects prior control epoch immediately but still enforces <=24h and whitelist; OMSIdentityVerifier rejects old controller/epoch and fails closed if registry evidence is unavailable/stale; authorization cache evicts prior-epoch entries and denies until fresh proof. Confirm stable DID/NFT resolves to new controller/epoch. Test each consumer with old and new evidence after recovery.
21. Classify tests by layer: pure helper/property tests may exercise duplicate signatory list entries and encoding ambiguities; Plutus V3 script tests use only ledger-valid signer sets and complete contexts; target evaluator tests cover actual interval and redeemer semantics; ledger-admission and live Pre-Prod evidence remain separate and are not inferred from simulations.

## Mutation sensitivity and evidence

22. Mutate away each quorum threshold, distinct-signer check, PoP, timelock boundary, bounded validity width, request-domain field, nonce/epoch increment, freeze lock, continuity/value check, exact token continuation, and admin-denial rule. The targeted suite must fail for every mutation.
23. Run compiled public validators using complete Plutus V3 contexts, realistic signer sets, validity intervals, inputs, outputs, mint/burn, redeemers, datum hashes, and value maps. Validate against the target Cardano evaluator/ledger; a Python design model or local helper passing is not acceptance.
24. Record design simulations separately from Aiken unit/property tests, compiled evaluator tests, ledger admission, and live Pre-Prod evidence. This draft executed none of them.

28. Counter overflow: for each state transition that increments `state_nonce`, set it to `2^64-1` and assert rejection without wrap or output; set `control_epoch`/`guardian_epoch` to `2^64-1` and assert controller/guardian rotation rejects. 29. Atomic standalone registration: the standalone policy rejects minting with no registry-script input, with a wrong registry script hash, or with more than one matching registry input; rejects zero matching registry outputs, duplicate matching outputs, a wrong output datum/identity tuple, or an output lacking the minted token. Accept only the same transaction with exactly one designated bootstrap input, exactly one matching registry-script input, one +1 minted token, and exactly one registry-script output with matching inline datum/token. Confirm the registry spend is executed and rejects any non-`RegisterAgent`/invalid redeemer; a passing mint policy alone is insufficient.
30. Transaction-signature PoP substitution: reject genesis when the founding owner, initial controller, or any one of five guardians is absent from the ledger-validated signer set (one signature covers founder/controller only when their VKHs are equal); reject routine/recovery rotation without the destination controller signer; reject guardian rotation unless all five proposed guardians sign. Reject signatures for a different request ID, identity token, bootstrap reference, destination controller, guardian set, or guardian epoch. Tests use complete ledger-valid contexts and do not model a detached signature as PoP.

31. DID bounds: accept well-formed UTF-8 values of exactly 32 and 256 bytes; reject 31-byte and 257-byte values and malformed UTF-8. Count encoded bytes without Unicode normalization and verify the u16 length prefix matches the exact accepted byte sequence.
